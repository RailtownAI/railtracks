# Upgrading to 1.9.0

Railtracks 1.9.0 lets a message mix text and attachments in any order, such as "this chart, then that chart". To support that, every message now follows one rule: **`.content` is a list of parts, in order**. A part is text (`str`), an `Attachment`, or, on an assistant turn, a `ToolCall`. Read text with the new `.text` property, attachments with `.attachments`, and tool calls with `.tool_calls`.

!!! warning "1.9.0 is a minor release with a breaking change"
    Version pins such as `railtracks>=1.8` or `railtracks~=1.8` will pick up 1.9.0 automatically. If you are not ready to migrate, pin `railtracks==<YOUR VERSION>`.

---

## What changed

Creating user, assistant and system messages is unchanged: `UserMessage("Hi")`, `AssistantMessage("Hi")`, `SystemMessage("Be brief.")`, `attachment=` and `rt.call(agent, "Hi")` still take a string, which is stored as a one-item list. What changes is what you read back from `.content`, plus the way a `ToolMessage` is built.

| Reading | Before | Now |
|---|---|---|
| `UserMessage("Hi").content` | `"Hi"` | `["Hi"]` |
| `UserMessage("Look", attachment="a.png").content` | `"Look"`, with the image on `.attachment` | `["Look", Attachment(...)]` |
| `AssistantMessage("Hi").content` | `"Hi"` | `["Hi"]` |
| `SystemMessage("Be brief.").content` | `"Be brief."` | `["Be brief."]` |
| `result.content` for a text agent | `"Hi"` | `["Hi"]` |
| A tool-calling turn's `.content` | `ToolCalls([call], text="Checking.")` | `["Checking.", call]` |
| A tool result's `.content` | `ToolResponse(identifier="c1", name="weather", result="18°C")` | `["18°C"]`, with `.tool_call_id` and `.name` on the message |
| Text of any message or result | `.content`, `.content.text` or `.content.result` | `.text` |
| Attachments of a message | `UserMessage.attachment` (`list` or `None`) | `.attachments` (`list`, empty when there are none) |
| `result.tool_invocations` | `(ToolCall, ToolResponse)` pairs | `(ToolCall, ToolMessage)` pairs |

Unchanged: structured output is still your pydantic model, on both `result.content` and `result.structured`. The session JSON written for each run keeps its shape: text-only content is still saved as a string, a tool-calling turn is still saved as its list of calls with the spoken text beside it, and a tool result is still saved as `{"identifier", "name", "result"}`.

The old forms of building tool messages still work for one release and emit a `DeprecationWarning`: `ToolCalls(...)`, `ToolMessage(ToolResponse(...))`, `ToolMessage.result` and `ToolMessage.identifier`.

## Read results with `.text`

```python
# before
result = flow.invoke("What's the weather in Paris?")
print(result.content)

# after
print(result.text)
```

`.text` joins the text parts with newlines. It exists on every message (`UserMessage`, `AssistantMessage`, `SystemMessage`, `ToolMessage`), on agent results (`StringResponse`, `LLMResponse`) and on `rt.llm.Response`. Code that kept using `.content` gets a list, so `print(result.content)` prints `['...']`, `result.content + "..."` raises `TypeError`, and `file.write(result.content)` raises `TypeError`.

Passing one agent's result straight to another still works: `rt.call(next_agent, result.content)` sends the same text and attachments as a new user message. `rt.call(next_agent, result.text)` sends the text only.

On a structured-output agent, `result.text` raises `TypeError`; keep reading `result.structured`.

## Replace `isinstance` checks on `.content`

This is the pattern most likely to break quietly. A check such as `isinstance(message.content, str)` used to be true for every user, assistant and system text message. It is now **always false**, so code behind it stops running without raising: a custom guard that scanned for a keyword would allow everything.

```python
# before
@rt.input_guard
def block_passwords(event):
    for message in event.messages:
        if isinstance(message.content, str) and "password" in message.content.lower():
            return rt.guardrails.GuardrailDecision.block(reason="No passwords.")
    return rt.guardrails.GuardrailDecision.allow()

# after
@rt.input_guard
def block_passwords(event):
    for message in event.messages:
        if "password" in message.text.lower():
            return rt.guardrails.GuardrailDecision.block(reason="No passwords.")
    return rt.guardrails.GuardrailDecision.allow()
```

The same applies to `isinstance(message.content, ToolCalls)` and `isinstance(message.content, ToolResponse)`, which are now always false. Search your code for `isinstance(` next to `.content`, and for `.content` used as a string (`.lower()`, `in`, `+`, slicing, `re.search`).

On a message, `.text` is `""` for structured output and holds the text a model spoke alongside its tool calls. Output guards already skip tool-calling turns, so they only see final replies.

The built-in guards (`BlockText`, `PIIRedact`, `Scope`, the length guards) and `ConversationMemory` are already migrated. `PIIRedact` now redacts each text part of a message and leaves attachments where they are.

## Tool-calling turns

The text a model speaks with its tool calls now sits in `.content` next to the calls, in the order the model produced them, instead of on a separate `ToolCalls.text` attribute. Find a tool-calling turn with `message.tool_calls`, which is empty for any other turn.

```python
# before
if isinstance(message.content, ToolCalls):
    spoken = message.content.text
    for call in message.content:
        print(call.name, call.arguments)

# after
if message.tool_calls:
    spoken = message.text
    for call in message.tool_calls:
        print(call.name, call.arguments)
```

To build a tool-calling turn yourself, for example in a custom model or a test, put the calls in the content:

```python
# before
AssistantMessage(ToolCalls([call], text="Checking."))

# after
AssistantMessage(["Checking.", call])
```

Code that already read `message.tool_calls` needs no change.

## Tool results

`ToolMessage` holds the tool's answer directly, like any other message, with the call it answers on `.tool_call_id` and the tool on `.name`. `ToolResponse` is no longer needed.

```python
# before
message = ToolMessage(ToolResponse(identifier="c1", name="get_weather", result="18°C"))
print(message.content.result, message.content.identifier, message.content.name)

# after
message = ToolMessage("18°C", tool_call_id="c1", name="get_weather")
print(message.text, message.tool_call_id, message.name)
```

`result.tool_invocations` now pairs each `ToolCall` with its `ToolMessage`. `ToolMessage.result` and `ToolMessage.identifier` still work with a `DeprecationWarning`, so a loop such as `for call, response in result.tool_invocations: print(response.result)` keeps running while you move it to `response.text`.

Code that reads `message.content.result`, `message.content.name` or `message.content.identifier` on a tool message, for example in a custom model, must move to `message.text`, `message.name` and `message.tool_call_id`.

What your tools return is unchanged: a tool's return value is still sent to the model as text.

---

## System messages

`SystemMessage(...).content` is a list of text parts. Read the instructions with `.text`. A system message also accepts a list of strings, such as `SystemMessage(["Be brief.", "Answer in French."])`, and raises `TypeError` for an attachment. It is still sent to the provider as one string.

---

## Attachments

`UserMessage(text, attachment=...)` works as before and places the attachments after the text. To put them in a specific order, pass a list:

```python
before = rt.llm.Attachment("before.png")
after = rt.llm.Attachment("after.png")
message = rt.llm.UserMessage(["Before:", before, "After:", after, "What changed?"])
```

An agent accepts the same list as its input. See [Text and attachments in order](../agent_design/llms/modalities.md#text-and-attachments-in-order).

`UserMessage.attachment` still works but emits a `DeprecationWarning`; read `.attachments` instead. A message with only an attachment no longer gets an empty text part.

---

## Smaller changes

- **`Response.text`** on `rt.llm.Response` returns the text spoken alongside tool calls instead of raising. It still raises `TypeError` for structured output.
- **`str(message)`** for a message with several parts puts each part on its own line, showing tool calls as `name(arguments)` and attachments by their `repr`. A text-only message prints as before, for example `user: Hi`, and a tool message prints as `tool: get_weather -> 18°C`.
- **Error text.** When a model returns no usable reply, the `LLMError` now says `expected text` (or `expected text or <YourSchema>`) instead of `expected str`.
